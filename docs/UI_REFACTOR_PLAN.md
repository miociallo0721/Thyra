# Thyra UI 重构方案

> 状态：设计与实施计划，尚未开始产品代码改造。
>
> 整理日期：2026-09-25。
> 范围：当前原生 Android 纵向功能切片——连接、认证、Agent、会话和聊天。文件、终端、桌面等未来功能不在本轮实现范围内。

## 1. 目标与已确定方向

目标是让用户在任何屏幕尺寸下，始终清楚当前服务器、Agent、会话和连接状态，并顺畅完成「找到会话 → 阅读结果 → 继续输入」。保留原生 Compose、内容优先的布局，不引入 WebView。

本轮讨论收敛出的视觉方向：

- **浅色主题优先**：先完成一致的浅色体验，后续再单独设计深色主题。浅色主题不应在系统切换到深色模式时局部变暗。
- **低饱和浅绿**：以鼠尾草绿和暖白为主，不使用高饱和荧光色。
- **简约背景**：使用近乎均匀的浅绿白背景，不使用大块模糊色斑、复杂渐变、波浪或装饰图案。
- **局部毛玻璃**：顶栏、工具活动、输入区可使用轻透玻璃；长篇回复保持高对比、近乎不透明的阅读表面。玻璃用于区分层次，不覆盖所有内容。
- **克制动效**：动画帮助理解导航、状态变化和展开关系，不为流式输出或背景持续制造运动。

此前的效果图只用于确定视觉意向，不是当前应用截图，也不是像素级实现规格。实施前需在当前代码上重新截取基线图。

## 2. 现状审查摘要

已有基础：浅深色 Material 3 配色、间距 token、稳定的 Agent/会话/消息列表 key、默认折叠的推理和工具活动、手机分层导航及宽屏会话/聊天双栏。流式聊天的断线恢复与历史对账已经建立，应原样保留。

需要优先解决的问题：

1. 宽屏未选会话时右侧为空白；当前固定 360dp 会话栏尚未照顾大字和窗口变化。见 `app/src/main/java/dev/thyra/android/ThyraApp.kt`。
2. 聊天顶栏只显示 Agent，会话身份不明显；会话列表选中态仅靠细微位移，更新时间也没有展示。见 `feature/chat/src/main/java/dev/thyra/feature/chat/ChatScreen.kt` 与 `feature/sessions/src/main/java/dev/thyra/feature/sessions/SessionsScreen.kt`。
3. 历史加载中可能先显示真正空会话的文案；连接失败缺少清晰的恢复动作。需要分开加载、空、错误和断线状态。
4. 聊天草稿使用未按会话分组的本地保存状态，重构时应明确按服务器、Agent、会话隔离。
5. 设计系统尚未覆盖完整的语义色、排版、形状、容器、状态与动效 token；各页面有较多直接写入的尺寸和文案。
6. 点击行、折叠控件及状态反馈需要补足读屏标签、展开状态和可触达范围。
7. 动效目前主要是折叠区的 `AnimatedVisibility`、加载指示器及 Navigation 3 默认行为；聊天更新使用 `scrollToItem()` 即时定位，尚无统一动效规则。

## 3. 浅色视觉规格草案

以下值是第一轮设计 token 候选；最终颜色以真实设备上的对比度和截图校准为准。

- 页面背景：`#E8EFE8`，均匀的低饱和浅鼠尾草绿。
- 内容表面：`#FBFCF9`；长文阅读区域可更接近白色。
- 主色：`#456D5A`；主按钮、当前选中、连接成功等关键强调使用深绿，不用浅绿承载白字。
- 浅绿容器：`#DDEBDF`；用于用户消息、头像底色和轻量选中面。
- 次级绿色：`#E5EDE4`；用于低强调操作和少量状态面。
- 正文：`#202B23`；次要文字：`#526157`。
- 分隔与轮廓：`#D1DBD1`；不要用深边框包裹每个区块。
- 错误：低饱和玫瑰红 `#A35651`，浅色容器 `#F7E7E3`；错误不借用成功绿。

毛玻璃组件的初始规则：

- 采用乳白半透明表面、细亮边和短而轻的阴影；透明度应保证正文和控件始终可读。
- 顶栏和输入栏允许较强的玻璃层次；Agent/会话列表仅在需要明确分组或选中时使用轻透表面，避免满屏重复卡片。
- 助手长文、代码和工具输出使用高对比的稳定阅读面，不能因为玻璃而降低可选中内容的清晰度。
- 背景保持静态。玻璃的模糊半径不参与持续动画。
- Android 最低支持 API 26。Compose 的普通 `Modifier.blur` 作用于自身内容，不能直接等同于背景毛玻璃；Android 12 以下应使用近似的半透明着色表面。真正的背景模糊只在验证可读性和性能后启用。

视觉上保留扁平、内容优先的原则。字体以清晰的无衬线中文为主，页面标题、列表标题、正文、时间与状态使用固定层级；不要通过大量阴影或圆角制造层次。

## 4. 页面与适配方案

### 连接与认证

- 首页优先展示最近服务器与 Memoh Cloud；「新增自托管服务器」进入独立、聚焦的填写与验证流程，演示入口保持可发现。
- 认证页明确区分 Cloud 验证码、密码和访问令牌模式；忙碌与错误状态出现在对应操作附近。
- 系统栏与键盘出现时保持浅色主题和可见操作，不让半透明输入区覆盖表单。

### Agent 与会话

- Agent 行稳定展示头像、名称与可用状态；不可用项解释原因，整行提供读屏动作标签。
- 会话行展示标题和更新时间；当前会话使用明确的背景、文字和语义状态共同表达选中。
- 空列表给出下一步操作；宽屏未选会话时，右侧显示 Agent 身份和「选择或新建会话」引导。

### 聊天

- 顶栏同时表达 Agent 与当前会话；连接、重连、生成中、权限异常各有稳定的位置和文案。
- 用户消息使用浅绿容器；助手正文保持开放或近白阅读面。推理和工具活动继续默认折叠。
- 工具活动可用轻玻璃表面，长输入/输出需有完整查看与复制路径。
- 草稿按服务器、Agent、会话隔离。重连或错误时已有转录保持可见，输入状态与是否可发送一致。

### 屏幕尺寸

- 手机保留分层导航，返回后恢复原列表位置。
- 中等宽度采用会话列表与聊天双栏；足够宽时再考虑 Agent 导航栏。
- 栏宽设置上下限，聊天正文设置合理阅读宽度；字体放大后允许退回更少的栏数，而不是压缩文字。
- 窗口缩放、旋转和导航动画不应丢失当前会话、阅读位置和草稿。

## 5. 动效规格草案

动效关键词：**轻、短、可中断**。用户操作的状态变化应立即生效，动画只负责解释变化。

- 快速反馈：约 **100–140 ms**。用于按下反馈、发送/停止图标切换、状态标签淡换。
- 局部展开：约 **180–220 ms**。用于推理和工具活动展开/收起、箭头旋转；长内容避免整块反复测量和拉伸。
- 页面导航：约 **220–260 ms**。手机前进时小幅水平位移加淡入，返回反向；预测返回与系统手势一致。
- 宽屏切换会话：只在聊天区域进行短淡换，不移动整个工作区。
- 聊天滚动：初次打开历史直接定位底部；用户停在底部且出现新消息时平滑滚动；流式文本逐步增长时维持底部，不对每个增量启动新滚动；用户上滑阅读后不强制拉回。
- 加载与错误：局部反馈优先，避免整页闪烁、骨架屏反复重启和无限呼吸动画。
- 毛玻璃背景、模糊半径与大面积色块不做循环动画。

尊重系统动画比例与关闭动画设置：比例为零时直接显示最终状态，信息和操作不依赖动画才能被发现。

## 6. 建议实施顺序

1. **基线**：在当前版本记录连接、认证、Agent、会话和聊天的加载、空、错误、断线、流式状态；覆盖 360dp 手机、840dp 附近窗口、宽屏、浅深系统设置和大字比例。旧演示截图摄于 2026-09-19，不能当作最新视觉基线。
2. **设计系统**：补全浅色语义色、排版、形状、表面、间距、动效 token 与文案资源；确定系统栏和 API 26 回退效果。
3. **共享组件**：制作工作区顶栏、Agent/会话行、状态区、错误恢复、活动披露、玻璃表面和输入栏；先在一个页面验证，再跨页面复用。
4. **页面与信息结构**：依次重构连接/认证、Agent/会话、聊天；同时处理宽屏空状态、会话身份、选中态和草稿隔离。
5. **动效与性能**：统一导航和局部动效，调整聊天滚动；在流式输出和低端设备上验证玻璃与动画成本。
6. **回归验收**：完成可访问性、深色系统下的固定浅色外观、键盘、旋转、后台恢复和真实服务器烟测。

## 7. 验收标准

- 同一套语义色在所有页面一致；正文、次级文案、按钮和状态在真实设备上清楚可读。
- 背景简约且静态，毛玻璃能体现层次，但不影响长文、Markdown、代码和工具输出阅读。
- 用户始终能识别服务器、Agent、会话以及连接状态；宽屏没有无解释的空白区域。
- 加载、真正空内容、断线和请求失败分别呈现；错误有恢复路径，已有转录不消失。
- 大字、TalkBack、触控和键盘可完成主要流程；动画关闭后功能与状态依然完整。
- 连续流式输出、新消息、上滑阅读、展开工具、切换会话和打开键盘时无明显跳动；用真实设备的帧时间数据与基线比较。
- 每个实施阶段交付前运行 `.\gradlew.bat test` 与 `.\gradlew.bat assembleDebug`，并完成相关设备回归。

## 8. 不可破坏的边界

- 保持 `features -> core:model + core:designsystem`、`core:data -> core:model + core:network`、`app -> features + core:data` 的依赖方向。Compose 不直接调用 OkHttp。
- 不把凭据放进 DataStore、Room、日志、URL、截图或测试夹具。生产构建维持禁用明文流量，不绕过 TLS 验证。
- 不新增 WebView 面板，也不猜测 Memoh API。若后续 UI 需求涉及 API 变化，先检查当前 Memoh OpenAPI、Go handler 与 Web client，并在 `docs/API_NOTES.md` 记录所检查提交。
- 流式聊天保留稳定的 `invocation_id` / `control_id`、严格的 epoch 与连续序列规则、缺口时请求权威快照、运行结束后由 REST 历史对账，以及连接错误时保留已有转录。

## 9. 实施时再验证的选择

- 全局浅色固定到什么阶段，以及是否提供用户可选深色主题。
- 真实背景模糊的技术实现、API 26–30 回退方式和各设备性能；不把概念图当作实现承诺。
- 玻璃透明度、圆角和阴影的最终数值，以长文本、大字和室外可读性测试为准。
- 宽屏是否增加常驻 Agent 栏，取决于完成双栏与会话切换后的实际使用验证。
